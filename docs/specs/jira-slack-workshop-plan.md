# План реалізації воркшопу Jira та Slack

Ціль першої інтеграційної версії — живий Slack-тред, схвалення репортера й підтверджений запис у навчальну Jira. Далі додаємо Jira Cloud і повну вкладку прогонів. [Специфікація воркшопу](jira-slack-workshop-spec.md) визначає узгоджений сценарій і межі вправи.

## Вихідна точка

У репозиторії вже є FastAPI, локальна база з міграціями, worker, headless-запуск Claude зі структурованим результатом, журнал подій і React-дашборд із SSE. Використовуємо їх як основу. Поточна модель `Task` і переходи орієнтовані на PR та CI. Jira-прогони отримають окремий життєвий цикл і API. Поточний Slack Incoming Webhook для CI залишається окремим від бота воркшопу. Джерела для перевірки в репозиторії — [архітектура CI](../ARCHITECTURE.md), [runner](../../backend/app/integrations/claude_runner.py), [потік SSE](../../backend/app/api/stream.py) і [Slack-сповіщення](../../backend/app/integrations/slack.py).

## Етап 0. Перевірка інтеграційних передумов

1. Підтвердити Slack workspace, канал і доступ організатора до встановлення застосунку. Перевірити приймання повідомлення з треду, дії кнопки й повідомлення з кодом у діалозі з ботом.
2. Перевірити запуск на двох типових середовищах учасників або, якщо доступне одне, зафіксувати підтриману конфігурацію. Зафіксувати перевірену версію Claude Code, спосіб доступу до моделі й мінімальний приклад `claude -p` із делегуванням, структурованим результатом і двома hook-подіями.
3. Обрати адресу маршрутизатора, доступну з ноутбуків. Для реалізації пропонується Socket Mode між Slack і маршрутизатором та вихідне HTTPS-опитування локальними екземплярами. Це прибирає потребу в публічному порту на кожному ноутбуці. Перевірити проксі та корпоративні обмеження мережі на місці проведення.
4. Запросити доступ до тестового Jira-проєкту паралельно з підготовкою. Уточнити Cloud чи Data Center, політику облікових даних, роль репортера й право редагувати опис.

**Вихід.** Відомо, як запустити Claude, де працюватиме маршрутизатор та хто налаштує Slack. Статус доступу до Jira задокументовано. Невизначений доступ до Jira не затримує навчальний цикл. [Slack Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/) · [Налаштування Claude Code](https://code.claude.com/docs/en/settings)

## Етап 1. Докази багу, навчальна Jira та стан прогону

### Фікстура

- Зробити невеликий сервіс зі станом місткості та листом очікування. Задати обидва зчитування залишку перед підтвердженнями через контрольовану синхронізацію в тесті. Окремо перевірити, що звичайне послідовне бронювання поводиться очікувано.
- Додати інструкцію запуску тесту й короткий Jira-опис. Тест з відтворенням дефекту запускається окремою командою. Штатні тести перевіряють, що фікстура демонструє очікуване падіння, якщо цей сценарій включено в автоматичні перевірки.
- Підготувати одну повну відповідь репортера, одну неповну й один запит на правки. Використати ті самі матеріали у демо, тестах workflow та офлайн-вправі.

### Контракти джерела й локальні записи

- Адаптер джерела має операції отримання ідентичності, пошуку задач `New` за репортером, читання однієї задачі й доповнення опису погодженим блоком. Створення тестового багу — окрема можливість навчального адаптера.
- Визначити поля нормалізованої задачі: джерело, ID, ключ, назва, статус, ID репортера, опис, доступне посилання, ознака версії опису. Зберігати початковий опис у його рідному форматі для запису, а агенту давати текстове представлення.
- Додати локальні записи для профілю підключення, прогону, чернетки, рішення, подій та операцій доставки або запису. Чернетка фіксує текст і версію джерельного опису. Рішення посилається на незмінну версію. Унікальні ключі захищають від повторного прогону, повторної доставки й подвійного застосування рішення.
- Вбудувати polling scheduler у локальний worker. За один тик обмежити вибірку, пройти сторінки адаптера й відокремити помилки інтеграції від прогонів. Scheduler запускається після готовності профілю. Перезапуск відновлює активні прогони й пропускає завершені. Для навчання запропонувати короткий конфігурований інтервал, наприклад п’ять секунд.

**Вихід.** Навчальний endpoint зберігає опис після перезапуску. Фікстура стабільно відтворює баг. Два різні репортери отримують лише свої задачі. Кілька тиків scheduler і перезапуск не дублюють локальний прогін.

## Етап 2. Наскрізний цикл зі справжнім Slack

### Підключення і доставка подій

- Додати до локального дашборда мінімальний екран підключення. Екземпляр запитує в маршрутизатора короткоживучий одноразовий код і показує його користувачу. Після повідомлення боту маршрутизатор прив’язує підтверджений Slack ID і видає локальному екземпляру окремий обліковий запис підключення. Локальні API та журнали не показують повторно секрет підключення.
- Маршрутизатор приймає Slack-події, відокремлює підтвердження отримання від запуску моделі, зберігає маршрути й буферизує вхідні події до підтвердження локальним екземпляром. Фільтрує сторонні workspace, канали та повідомлення бота. Зберігає стабільний ключ події та порядок у треді. Локальний обробник застосовує переходи послідовно для кожного прогону.
- Для відкриття треду локальний проєкт надсилає ключ операції, ключ задачі й підготовлений текст. Маршрутизатор зберігає відповідність ключа операції Slack-треду. Після успішного створення локальний проєкт отримує посилання. Якщо результат створення треду невідомий, перед повторним викликом звіряємо зовнішній результат або зупиняємо прогін для перевірки.
- Публікацію уточнення, чернетки, запиту правок і фінального повідомлення оформити як окремі операції. Кнопки передають непрозорий ID версії. Маршрутизатор перевіряє зв’язок події з тредом і власником маршруту, а локальний workflow перевіряє право репортера й стан. [Slack Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/) · [Типи Slack interactivity payloads](https://docs.slack.dev/reference/interaction-payloads)

### Headless-етапи

- Використати спільні частини чинного runner, що запускають Claude, обмежують час і читають структурований результат. Перевірити потребу в окремій навчальній конфігурації, бо наявний runner готує спільний каталог із власними налаштуваннями. Для воркшопу завантажувати актуальні агенти, skill і налаштування hook з явно визначеної локальної папки. Розвести робочі каталоги одночасних запусків.
- Описати вхід і вихід кожного етапу. Початковий тріаж приймає опис і докази, а повертає повідомлення з уточненнями. Обробка відповіді приймає історію, питання, ліміт перепитувань і результат розслідування, а повертає уточнення або блок і текст запиту на схвалення. Правки приймають останню чернетку та коментар репортера, а повертають наступну версію. Фінальне повідомлення отримує фактичний результат запису.
- Для кожного виклику журналювати етап, ID запуску та підсумок. На некоректному результаті, помилці моделі або таймауті показувати стан і зберігати контекст для контрольованого повтору. Повідомлення агента в Slack формує Communication Agent із Tone of Voice skill. Для недоступної моделі передбачити короткі службові повідомлення бекенду з тією самою редакційною домовленістю.

### Схвалення і запис

- Транзакційно зафіксувати одне рішення на актуальну чернетку. При «Попросити правки» закрити стару версію й чекати пояснення. При «Схвалити» записати ID репортера, час, версію та намір запису. Старі кнопки деактивувати в Slack, якщо можливо. Локальна перевірка відхиляє їх незалежно від стану інтерфейсу.
- Зберігати результат Jira й доставку фінального Slack-повідомлення окремо. При тимчасовій помилці доставки повторювати саме повідомлення. Після таймауту запису перевірити, чи блок уже застосований. При зміні опису або непідтвердженому результаті показати причину й залишити запис на ручну перевірку.
- Перевірити сценарій з перервою підключення між відповіддю Slack і локальною обробкою. Після відновлення та сама подія має бути опрацьована один раз. Виміряти час від створення навчальної задачі до появи прогону й окремо тривалість запусків Claude.

**Вихід.** Перший живий прогін повністю працює з навчальною Jira. Є окремі перевірки успіху, правок, подвійного натискання, стороннього схвалення та повторної доставки. Поточний CI-сценарій проходить штатні перевірки.

## Етап 3. Jira Cloud

- Додати в дашборд підключення до дозволеного тестового проєкту, перевірку акаунта й читання задач. Облікові дані лишаються локально. Підтвердити спосіб авторизації після перевірки політики організатора. Розділити помилки підключення, відсутність прав і відсутність задач для поточного репортера.
- Реалізувати пошук з пагінацією та фільтром за проєктом, статусом і репортером. Окремо перевірити нормалізацію акаунта, зміну режиму при відкритому прогоні й повторний polling після запису.
- Зберігати початкову структуру ADF. Сформувати нові вузли для погодженого блоку й додати їх до наявного документа. Запит редагування змінює лише опис. Для першої версії перевірка перед записом виявляє вже наявні зміни опису. Можливість атомарної умовної зміни слід підтвердити для цільового API. До підтвердження використовуємо окремий тестовий проєкт і перевіряємо запис після виклику.
- Прогнати контрактні тести на зразках ADF з абзацами, списками, посиланнями й порожнім описом. Перевірити відмову доступу, таймаут і збереження початкового тексту. За наявності доступу виконати один живий прогін у тестовому проєкті.

**Вихід.** Реальна Jira виконує той самий контракт і змінює тільки опис. Без доступу адаптер перевіряється на підготовлених API-відповідях, а жива перевірка залишається окремим пунктом готовності інтеграції. [Пошук Jira Cloud](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/) · [Редагування задач Jira Cloud](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/#api-rest-api-3-issue-issueidorkey-put)

## Етап 4. Хронологія й навчальний hook

- Додати окремі маршрути списку та деталей Jira-прогонів. Узгодити повідомлення про стан підключення, помилки, очікування відповіді, правки, схвалення, запис і підтвердження. Оновлювати хронологію через наявний механізм SSE або окремий тип подій у ньому після перевірки сумісності.
- Показати джерело, ключ задачі, репортера, посилання на тред, версії чернетки й результат. У навчальному режимі додати створення багу та перегляд збереженого опису.
- Підготувати змінний hook для `SubagentStart` і `SubagentStop`. Передавати ID запуску з локального runner, приймати тільки події цього запуску, записувати час і тип агента. Для локальної реалізації пропонується окремий журнал запуску, який worker переносить у базу. Дедуплікація має відрізняти повторне читання запису від нового старту того самого subagent.
- Перевірити, що прогін із відсутнім або помилковим hook має зрозумілу діагностику, а історія завершеного прогону читається після перезапуску. Виклик агента в моделі й факт отримання hook-події показувати окремо, якщо доступні обидва сигнали.

**Вихід.** Учасник змінює hook, запускає headless-прогін і бачить фактичні події делегування у своїй вкладці. CI-дашборд проходить регресійну перевірку. [Події Claude Code hooks](https://code.claude.com/docs/en/hooks)

## Етап 5. Матеріали, репетиція і готовність

- Чекліст перед зустріччю охоплює отримання проєкту, залежності, локальний запуск, перевірку Claude Code і доступу до моделі. Підключення до Slack кодом відбувається під час воркшопу.
- Сценарій ведучого містить короткий опис ролей, показ відтворення багу, перехід із Jira в Slack, одну довільну відповідь, огляд чернетки та підтвердження запису. Тривалість демо визначається за репетицією.
- Практика на 30–45 хвилин використовує готові інтеграції. Після підключення учасник змінює заготовки агентів і Tone of Voice skill, налаштовує hook та проходить свій прогін. У стислому форматі головний результат — одна зміна конфігурації агента й один повний прогін.
- Записати успішний прогін. Підготувати окрему локальну команду, яка програє заданий баг-репорт і відповідь через реальні агенти та показує питання й чернетку без Slack. Порівняти результати до й після зміни skill.
- Ведучий один проходить увесь шлях за чеклістом. За результатом уточнює час і вирішує, чи потрібна репетиція з другим учасником. До репетиції маршрутизацію між двома екземплярами вже покриває автоматизований тест.

## Контрольні перевірки

| Сценарій | Критерій приймання |
| --- | --- |
| Повторний polling і рестарт | Один прогін і один тред на задачу, у тому числі після успішного оновлення з незмінним `New`. |
| Два локальні екземпляри | Різні репортери бачать лише свої задачі. Події спільного каналу не перетинаються між прогонами. |
| Відповідь вільним текстом | Одна відповідь може закрити кілька питань. Workflow допускає один додатковий раунд і не вигадує пропущених деталей. |
| Правки | Jira зберігає початковий опис. Публікується нова версія, а старі кнопки не змінюють стан. |
| Схвалення | Лише репортер може погодити актуальну версію. Повторна подія або натискання не запускає другий запис. |
| Конкурентна зміна опису | Якщо перед записом виявлено новий опис, погоджена чернетка не перезаписує його. |
| Помилка після запису | Якщо Jira оновлено, але Slack недоступний, повтор підтвердження не доповнює опис удруге. |
| Headless і hook | Структурований результат відповідає схемі, а реальні виклики subagents видно у хронології локального прогону. |
| Відсутній доступ до Jira | Учасник створює і читає навчальну задачу та проходить увесь цикл зі справжнім Slack. |
| Відсутній Slack | Ведучий показує запис, а учасник може локально відтворити генерацію питань і чернетки після зміни skill. |

## Залежності та рішення перед декомпозицією

Критичний шлях першого демо проходить через тестову задачу, локальний стан, підключення спільного бота, етапи Claude та перевірений запис після схвалення. Тестовий сервіс і шаблони агентів можна готувати, поки організатор налаштовує Slack. Перевірка сумісності headless hook може початися окремо після визначення формату події. Повноцінна вкладка використовує погоджений контракт прогону й хронології. Справжня Jira залежить від контракту джерела та доступу до тестового проєкту. Остаточний запис демо залежить від стабільного живого прогону.

Перед поділом на задачі потрібно звірити три технічні припущення: доступ до Slack-застосунку й транспорт локальних екземплярів, тип Jira та спосіб входу, підтриману конфігурацію Claude Code для делегування і hooks. Ці перевірки відокремлюють зовнішні залежності від роботи, яку можна починати з навчальними даними.
