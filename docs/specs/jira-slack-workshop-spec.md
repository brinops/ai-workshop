# Специфікація воркшопу Claude Code Subagents

Тема зустрічі — **From AI Assistants to Autonomous Agents: Orchestrating Real-World Workflows**. Учасник адаптує спеціалізованих агентів, запускає їх headless і бачить, як делегування та рішення людини перетворюють нечіткий баг-репорт на задачу, готову до передачі. Основний прогін починається з Jira й завершується погодженим доповненням опису та підтвердженням у Slack.

Ця специфікація задає поведінку вправи. [План реалізації](jira-slack-workshop-plan.md) визначає порядок перевірок і критерії готовності.

## 1. Формат заняття

| Частина | Що відбувається |
| --- | --- |
| До зустрічі | Охочі отримують короткий чекліст, запускають проєкт локально й перевіряють Claude Code та доступ до моделі. Доступ до Jira опційний. |
| Демо ведучого | Повний прогін з поясненням делегування, Tone of Voice, hook і схвалення. Тривалість визначаємо після репетиції. |
| Практика | Орієнтир 30–45 хвилин. Учасники підключаються до Slack кодом, адаптують заготовки subagents і правила делегування, редагують `SKILL.md` з одним прикладом, налаштовують hook та запускають свій прогін. |
| Резерв | Якщо Slack недоступний, ведучий показує запис успішного прогону. Учасники локально запускають агентів на готових даних і порівнюють питання, чернетку та події делегування після своїх змін. |

Scheduler, Slack-бот, маршрутизатор, адаптери Jira, схвалення та інтерфейс даємо готовими. CI/CD залишається в окремому наявному демо. Основний Jira-прогін використовує код і тест як докази, а його єдина погоджена зовнішня зміна — доповнення опису задачі.

## 2. Навчальний баг

**Подвійне бронювання останнього місця.** У тестовій папці є малий сервіс бронювання і тест, який керує черговістю двох запитів без залежності від затримок або випадковості. Залишилося одне місце, двоє різних користувачів отримують підтвердження. Очікування для вправи — перше бронювання підтверджено, другий користувач потрапляє в лист очікування. Причина в коді пов’язана з рішенням на основі вже застарілого залишку.

Початковий опис: «Іноді система підтверджує два бронювання на одне місце». Приклад відповіді в Slack: «На події було одне місце. Ми з колегою одночасно натиснули “Забронювати” з різних акаунтів і обидва отримали підтвердження, хоча другий мав потрапити в лист очікування».

Investigation Agent знаходить файл, функцію й тест, які пояснюють поведінку. Блок для Jira містить передумови й кроки, фактичний і очікуваний результат та посилання на докази. Він відділяє встановлені факти від припущень. Тестове падіння очікуване й запускається окремо від штатного CI.

## 3. Учасники, Jira та Slack

- **Ведучий** встановлює один Slack-застосунок, готує спільний канал, запускає маршрутизатор і демонструє прогін. Склад учасників можна визначити на місці.
- **Репортер** запускає локальний проєкт, надсилає одноразовий код у діалог зі спільним ботом, отримує згадку в першому повідомленні, відповідає в треді та схвалює або просить правки.
- **Локальний проєкт** зберігає прогони, налаштування учасника та журнал. Він працює з одним активним джерелом для пошуку нових задач, а кожен уже відкритий прогін зберігає своє джерело. Перемикання режиму не змінює адресу запису для відкритого прогону.
- **Маршрутизатор** зберігає зв’язок між Slack workspace, каналом, кореневим повідомленням треду та локальним екземпляром. Події одного треду отримує екземпляр, який його відкрив. Кнопки також прив’язані до повідомлення з конкретною версією чернетки.

### Режими джерела

**Навчальна Jira за замовчуванням.** Після прив’язки до Slack учасник отримує тестовий ID репортера. Через дашборд він створює підготовлений баг-репорт і бачить початковий та доповнений опис. Навчальний endpoint зберігає задачі та зміни й підтримує той самий контракт читання та запису, що й реальний адаптер.

**Справжня Jira за бажанням.** Учасник підключає власний акаунт у локальному дашборді. Проєкт визначає ID поточного Jira-користувача й пов’язує його з підтвердженим Slack-акаунтом. Пошук обмежений тестовим проєктом, статусом `New` та полем `Reporter`. Для вправи учаснику потрібні права читання й редагування опису. Учасники обох режимів можуть працювати одночасно в одному Slack-каналі. У першому повідомленні треду й дашборді видно джерело.

Scheduler періодично перечитує доступні задачі, включно з тими, що існували до запуску. Стабільний ключ задачі складається з режиму, ідентифікатора джерела та незмінного ID задачі. Ключ Jira для показу людині зберігається окремо. Стан прогону переживає рестарт. Задача з активним або завершеним прогоном не породжує новий тред. Повторне підключення того самого локального екземпляра відновлює маршрут. Для одного репортера в межах однієї сесії воркшопу пропонуємо дозволяти один активний екземпляр, щоб два ноутбуки не забрали одну задачу.

## 4. Workflow і схвалення

| Стан | Подія і результат |
| --- | --- |
| Виявлено | Scheduler перевіряє джерело, репортера й дедуплікацію, створює локальний прогін і ставить відкриття Slack-треду в чергу. Дашборд може показати прогін одразу. |
| Тріаж | Бекенд запускає Claude headless з початковим описом і матеріалами демо. Claude визначає, яких деталей бракує. |
| Очікування відповіді | Бот ставить до трьох питань одним повідомленням. Репортер може покрити їх одним довільним повідомленням. Бекенд передає відповідь і збережений контекст у Claude. Допускається один додатковий раунд уточнення. |
| Очікування схвалення | Claude формує структурований блок і повідомлення. Бекенд зберігає версію й показує точний блок із кнопками «Схвалити» та «Попросити правки». |
| Очікування правок | Стара версія втрачає можливість схвалення. Репортер пише зауваження в тому самому треді. Claude готує нову версію, яку репортер бачить перед схваленням. |
| Схвалено | Бекенд фіксує хто, коли і яку версію погодив. Перевірка охоплює репортера, маршрут, прогін, поточний стан і версію. Схвалення атомарно створює один намір запису. |
| Застосовано | Бекенд перевіряє актуальну задачу, додає саме погоджений блок, фіксує успішний запис і ставить підтвердження в Slack у чергу. |
| Готово до передачі | Підтвердження успішно доставлено в той самий тред, і дашборд показує завершення вправи. Jira зберігає `New`. Якщо Slack тимчасово недоступний, дашборд показує, що зміни вже застосовано й підтвердження очікує доставки. |
| Потрібне втручання | Бракує фактів після додаткового уточнення, неможливо перевірити право на запис або результат зовнішньої операції невідомий. Дашборд показує причину та останній підтверджений крок. |

Сторонні повідомлення, повідомлення бота й дії сторонніх користувачів не змінюють стан прогону. Події дедуплікуються. Під час очікування схвалення нова відповідь сама по собі не змінює чернетку. Бекенд ніколи не трактує фразу в тексті як натискання кнопки. Якщо після уточнень лишаються прогалини, чернетка може явно їх позначити, якщо наявних фактів достатньо для корисного доповнення. Інакше прогін потребує втручання.

Перед записом адаптер перечитує задачу, перевіряє репортера й порівнює опис із версією, на якій побудовано чернетку. При помітній зміні опису прогін зупиняє запис і потребує перегляду. Після таймауту запису адаптер спершу звіряє зовнішній результат за стабільною ознакою операції або наявністю погодженого блоку. Невизначений результат переходить на ручну перевірку. Повтор доставки Slack-підтвердження відокремлений від запису Jira.

## 5. Claude Code і hook

| Роль | Вхід і результат |
| --- | --- |
| Triage Agent | Початкова задача або нова відповідь, стан і обмеження етапу. Координує делегування та визначає наступний результат етапу. |
| Investigation Agent | Баг-репорт, відповіді, локальний сервіс і тест. Повертає факти, прогалини й перевірювані посилання на докази. |
| Communication Agent | Факти й тип повідомлення. Використовує Tone of Voice skill для уточнень, запиту на схвалення, запиту правок і повідомлення про результат. Текст підтвердження спирається на результат запису від бекенду. |
| Action Agent | Контекст і підтверджені відомості. Повертає структуровану пропозицію доповнення опису. Бекенд перетворює її на запис лише після схвалення. |

Результати етапів валідуються за схемою. Контекст відновлюється з локальної бази між запусками Claude. Текст Jira, Slack і тестові матеріали передаються як дані. Claude отримує навчальні файли й локальну конфігурацію учасника. Облікові дані Slack і Jira залишаються у відповідних компонентах. Редаговані hooks виконуються в локальному середовищі учасника.

Hook на `SubagentStart` і `SubagentStop` зберігає час, назву й ID subagent, тип події та прив’язку до запуску. Дашборд бере ці дані з журналу, не виводячи секретів, повних транскриптів або локальних шляхів. Запуск верхнього рівня і фактичні виклики subagents показуються окремо. [Довідка Claude Code про hooks](https://code.claude.com/docs/en/hooks)

## 6. Дашборд і результат

Окрема вкладка **Jira Workflow** показує підключення Slack, активний режим Jira, локальні прогони, ключ і джерело задачі, стан, посилання на тред та причину помилки. Деталі прогону показують часову шкалу від виявлення задачі до запису, делегування, версії чернетки, хто й коли схвалив, та результат запису й підтвердження. У навчальному режимі в дашборді можна створити баг і перевірити збережений опис. CI-дашборд лишається окремим.

Мінімальний успіх вправи — один тред, перевірене схвалення репортера, одне доповнення опису без втрати оригіналу, повідомлення в Slack і видима хронологія делегування. Для першої репетиції цей шлях повністю проходить ведучий. Потребу в окремій репетиції з двома учасниками визначаємо за результатом.

## 7. Робочі припущення

Перший справжній адаптер плануємо для Jira Cloud. Організатору потрібно підтвердити тип Jira, тестовий проєкт, метод підключення, права й дозвіл на встановлення Slack-застосунку. Як транспорт Slack пропонуємо Socket Mode на маршрутизаторі та вихідне підключення локальних екземплярів. Це окремі технічні рішення для перевірки на ранньому етапі. Без доступу до Jira основний воркшоп проходить у навчальному режимі. [Slack Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/) · [Jira Cloud REST API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/)
