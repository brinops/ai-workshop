# Аудит: розширення CI Control Plane до Event-Driven AI Operations Platform

**Дата:** 2026-10-30 · **Стан коду:** `main` @ `680ba2b` · **Статус:** аудит і пропозиція, реалізацію не розпочато

**Як перевірено:** прочитано бекенд (моделі, worker, API, запуск агентів, routing), запущено тести (87 passed), проведено два експерименти з `claude -p` на безпечних фікстурах (розділ 2). Фронтенд переглянуто лише за структурою файлів. Оцінки — приблизні, для одного розробника.

## 1. Висновок

**Розширення без переписування можливе.** Запуск агентів, audit log, SSE, leases і дії з перевіркою стану можна використати повторно. Але модель даних, routing і worker написані під сценарій «PR → CI → виправлення», тому нові джерела треба додавати **поруч із ним**, а не перебудовувати `Task`.

Рекомендація: новий невеликий шар `inbound_events` + `workflow_runs`, а наявний CI-пайплайн лишається окремим workflow без змін логіки.

**Перед воркшопом обов'язково закрити:** дві знайдені вразливості (2.1, 2.2) і відсутню авторизацію дій (2.3). Це блокери, бо учасники запускатимуть власний код агентів на спільному сервері.

Розбіжності з вимогами (розділ 1 ТЗ): **scheduler у системі відсутній**. Є лише тік worker кожні 2 с, без розкладу. Звітів немає, окрім експорту `just export-run`.

## 2. Критичні знахідки

### 2.1. Skills і агенти завантажуються з PR (підтверджено)

`run_analysis` і `run_remediation` передають worktree PR через `--add-dir`, а цей прапор завантажує `.claude/skills` і `.claude/agents` з доданої директорії.

- **Експеримент:** skill з доданої директорії з'явився в init-події сесії, виконався, і агент повернув його маркер `PLANTED-7731`. Агент звідти також з'явився у списку. `settings.json` з `SessionStart` hook з тієї директорії **не** спрацював.
- **Слід у реальному прогоні:** у `docs/examples/pr-16-scenario-c/03-analysis/agent-transcript.jsonl` агент викликає `task-14-analysis-r13:k8s-failure-analysis`, тобто копію skill з worktree. Це дублює завантаження і, ймовірно, додає вартості.
- **Наслідок:** PR може підкласти інструкції агенту, який цей PR перевіряє. `docs/ARCHITECTURE.md:103` і кінець `docs/HOW_IT_WORKS.md` стверджують протилежне.
- **Не перевірено:** повний сценарій атаки через реальний PR.
- **Виправлення:** видаляти `.claude/` з worktree перед запуском агента і додати регресійний тест. Scope check уже обмежує, які файли може змінити виправлення, але не те, які інструкції читає агент.

### 2.2. `Read` не обмежений директоріями (підтверджено)

`--allowed-tools Read` без шляхів дозволяє читати будь-який файл, доступний користувачу процесу. В експерименті агент прочитав фейковий файл поза `cwd` і `--add-dir`, `permission_denials` порожній. `agent_env()` очищає змінні середовища, але **не файли**: `.env` лишається досяжним, а також `Grep` і `Glob`, найімовірніше, теж (окремо не перевірялись).

- **Наслідок:** prompt injection, а на воркшопі просто skill учасника, може прочитати секрети сервера і вивести їх у відповідь.
- **Виправлення:** запускати агентів учасників у контейнері без секретів і зі змонтованими лише потрібними директоріями. Правила `Read(...)` на шлях допоможуть як додатковий шар, але їх треба окремо перевірити.

### 2.3. Дії та налаштування без авторизації

`_check_token` викликається лише в `POST /tasks/register`. `POST /tasks/{id}/actions/{action}` і `PUT /settings/automation` доступні будь-кому, хто бачить сервер, а сервер уже запускався на LAN. Автоматизація до того ж глобальна: один учасник вмикає Auto Push для всіх.

### 2.4. Менші обмеження

| Де | Проблема | Наслідок |
|---|---|---|
| `prepare_agent_home` | Спільний `var/agent-home`; `rmtree` на кожен запуск | Паралельні запуски різних учасників псують один одного |
| `build_command` | Жорстко задано `Write all prose in English` | Tone of Voice українською не працюватиме без параметра |
| `max_concurrent_agents = 2` | Глобальний ліміт | Черга на воркшопі |
| `Approve Push` | Береться остання ремедіація, без прив'язки до SHA | Застаріла кнопка в Slack може схвалити новіший коміт |
| `Comment`, `AgentRun`, `Notification` | `task_id` обов'язковий | Не можна використати поза PR без міграції |
| Slack | Лише Incoming Webhook | Немає mentions, тредів і кнопок |

## 4. Відповіді на питання аудиту

1. **Що вже є:** PR/CI-цикл, headless-запуск, audit log, SSE, дії з перевіркою стану, Slack-сповіщення, dry-run для Helm.
2. **Без змін:** `state_machine`, `ci.py`, `github.py`, `git_worktree.py`, `redaction.py`, `record_event`, leases, SSE, `register_pr.py`.
3. **Потребують розширення:** `control_plane.py`, `claude_runner.py`, `worker.py` (новий диспетчер), `slack.py`, `actions.py` (`actor` уже є), моделі, дашборд.
4. **Кілька джерел і режимів:** зараз ні. `Task` вимагає `repo`, `pr_number`, `head_sha`. Зате `events.task_id` уже nullable, а SSE читає таблиці й тому готовий до нових подій.
5. **Ті самі skills в обох режимах:** так, якщо skill пише лише результат за контрактом і читає вхід з файлів. Skills не мають покладатися на мережу чи Bash: у headless вони заборонені. Дані готує бекенд заздалегідь, а дії виконує теж бекенд. **Обмеження:** hooks у headless не працюють (`prepare_agent_home` пише власний `settings.json`), і це правильно: hook учасника не має виконуватись на сервері.
6. **SessionStart briefing:** новий `GET /api/briefing?participant=…` і hook за зразком `emit()` з `register_pr.py` (`additionalContext`). Лише читання, таймаут 2–3 с, при недоступності сервера сесія стартує без briefing.
7. **Достатність моделей:** routing і approvals — ні, scheduler відсутній, history — так для PR і легко розширюється.
8. **Ізоляція:** розділ 6.
9. **Ризики:** розділ 8.
10. **Мінімальний набір:** розділ 7, фази 0–4 і 6.

## 5. Рекомендована архітектура

```text
GitHub ─ hook/polling ──▶ tasks (CI-пайплайн без змін) ──┐
Jira ─── polling ───┐                                    │
Slack ── Socket ────┼▶ inbound_events ▶ router ▶ workflow_runs
Scheduler ──────────┤                            │       │
Claude Code hook ───┘                     контекст з БД  │
                                                 ▼       ▼
                              claude -p (skill/agent) у контейнері
                                                 │ JSON + запитані дії
                                                 ▼
                         policy: роль + allowlist ▶ approval ▶ дія
                                                 ▼
                       Tone of Voice ▶ відповідь у вихідний канал + audit
```

**Рішення:**

- **`Task` не узагальнюємо.** Це найризикованіша зміна з найменшою вигодою: вона торкнеться worker, API, дашборда і 87 тестів.
- **Нові таблиці:**
  - `inbound_events`: `source`, `type`, `external_id`, автор, роль, `participant_id`, payload, статус, `UNIQUE(source, external_id)`;
  - `workflow_runs`: подія, workflow, статус, результат, опційний зв'язок із `task_id`;
  - `approvals`: дія, параметри, зокрема SHA, хто запросив, хто вирішив, термін дії;
  - `people` у конфігу: ідентифікатори Slack і Jira → роль.
- **`agent_runs` і `agent_log_lines`:** `task_id` стає nullable, додається `workflow_run_id`. Міграція SQLite через batch-режим.
- **Агент не має ані токенів, ані мережі.** Він повертає JSON із запитаними діями. Бекенд перевіряє їх за allowlist і роллю, тоді виконує. Це вже закладена модель, її лишаємо.
- **Tone of Voice отримує лише факти з попереднього кроку.** Окрема перевірка, що ключові значення (номери, SHA, статуси) збереглись у тексті, дає детермінований захист від вигаданих фактів.

Приклад конфігу (нова секція поруч із `repositories`, CI-маршрути без змін):

```yaml
workflows:
  - name: jira-triage
    on: {source: jira, type: issue_created}
    steps:
      - {skill: jira-triage, output: triage}
      - {skill: tone-of-voice, input: triage, output: reply}
    allowed_actions: [jira.comment]
    approval_required: [jira.transition]
```

**Jira:** у MVP polling через JQL. Публічний URL не потрібен, polling природно вписується в тік worker, а дедуплікація спирається на ключ тікета й час оновлення. Webhook можна додати пізніше.

**Slack:** Socket Mode (публічний URL не потрібен). Mentions, треди, кнопки. Кнопка викликає наявний `actions.perform(actor="slack:<user>")` після перевірки ролі та SHA. Дедуплікація за `event_id`, власні повідомлення бота ігноруються за `bot_id`.

## 6. Ізоляція учасників

| Що | Як |
|---|---|
| Здача роботи | Гілка `participant/<id>`. Сервер бере з неї **лише** `.claude/skills` і `.claude/agents` |
| Hooks | Працюють тільки на ноутбуці учасника. На сервер не потрапляють |
| Запуск | Контейнер на кожен запуск, без `.env`, власний agent home, ліміт бюджету |
| Інструменти | Визначає платформа, не файл учасника |
| Маршрутизація | Slack: канал або тег учасника. Jira: мітка `participant:<id>` |
| Дії в реальних системах | Лише над власними тікетами й тредами учасника |
| Автоматизація | Policy на workflow замість глобального перемикача для нових потоків |
| Перевірка | Однакові фікстури плюс приховані кейси, результат записується у scoreboard |

Працювати над однаковими фікстурами можна без Jira і Slack взагалі. Це і є dry-run режим, і він дає порівнянні результати, бо вхідні дані в усіх однакові.

## 9. Що потрібно вирішити

1. **Кількість учасників і тривалість.** Від цього залежать контейнери, бюджет і склад MVP.
2. **Дата воркшопу.** Чи вистачає часу на повний план, чи беремо скорочений.
3. **Де виконуються агенти учасників:** на спільному сервері, як рекомендовано вище, чи кожен локально зі своїм ключем. Локально простіше з ізоляцією, але потрібне встановлення в усіх, а спільний Slack однаково потребує сервера.
4. **Доступи:** Jira Cloud (інстанс, токен) і Slack App з правами бота.
5. **Оплата Claude:** спільний обліковий запис чи ключі учасників.
