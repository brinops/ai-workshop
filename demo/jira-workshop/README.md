# Заготовки агентів для Jira workflow

Агенти, skill і хуки воркшопу лежать у кореневій [`.claude/`](../../.claude). З кореня репозиторію Claude Code може викликати воркшопні ролі за іменами. Штатний runner копіює в тимчасову папку чотири ролі воркшопу, Tone of Voice skill і хуки делегування. Він передає етап, вхідні дані та `--json-schema` за W04, обмежує доступні інструменти й вимикає фонові задачі, щоб Triage дочекався відповідей спеціалістів.

| Роль | Що передає далі |
| --- | --- |
| `workshop-triage` | Визначає потрібних спеціалістів і збирає один результат етапу за W04. |
| `workshop-investigation` | Повертає факти з відповідей, посилання на код і тест та відсутні деталі. |
| `workshop-communication` | Формулює Slack-повідомлення з підвантаженим Tone of Voice skill. |
| `workshop-action` | Готує структурований блок для погодження репортером. |
| `workshop-planning` | Після передачі задачі складає план виправлення з кроками й критеріями приймання. |

На практиці можна змінити одне правило делегування в `workshop-triage.md` і тон у `SKILL.md`, а потім порівняти уточнення та чернетку на тих самих даних. Бекенд публікує повідомлення, керує версіями, перевіряє рішення репортера й записує погоджений блок. Штатний runner завантажує актуальну копію цього профілю для кожної спроби. Хуки `SubagentStart` і `SubagentStop` у `.claude/settings.json` записують тип та ID агента і час події. Runner переносить їх у хронологію з ID спроби.

Матеріали вправи доступні у [фікстурі W05](../booking/README.md). Форми результатів і приклади payload’ів описані в [контрактах W04](../../docs/specs/jira-slack-workshop-contracts.md). Поля профілю описані в [довідці Claude Code про subagents](https://code.claude.com/docs/en/sub-agents).

## Headless-запуск із worker

`Worker.run_workshop_stage(run_id, request, cancel)` приймає `StageInput` для `triage`, `reply`, `request_revision`, `revision` або `result`. Worker передає українську мову, схему поточного етапу й два файли фікстури в окремий тимчасовий каталог. Він перевіряє структурований результат перед поверненням. Після помилки або таймауту спроба зберігає діагностику й ознаку можливості повтору. `JIRA_WORKSHOP_AGENT_TIMEOUT_SECONDS` за замовчуванням дорівнює 120.

У локальному журналі є `workshop.agent_started` і `workshop.agent_finished` з одним `attempt_id`. Завершення містить статус, тип результату, назви викликаних спеціалістів і діагностику. Для нових прогонів навчальної Jira worker автоматично запускає діалог після відкриття треду. Він ставить уточнення, обробляє репліки, готує чернетку й після запиту правок публікує нову версію. За замовчуванням діалог увімкнено, якщо налаштовано Slack. `JIRA_WORKSHOP_DIALOG_ENABLED=false` вимикає автоматичний діалог. Після схвалення актуальної чернетки репортером worker один раз додає погоджений блок до опису в навчальній Jira й підтверджує запис у тому самому Slack-треді. Статус задачі залишається `New`.

На **Ready for handoff** worker автоматично готує і зберігає план. **«Взяти в роботу»** стає доступною, коли план готовий, і передає його агенту виправлення. План доступний у вкладці **Plan**, патч і тести — у **Diff** та **Validation**. Planner обирає маршрут із `jira_routes` у `control-plane.yaml`. Разом із планом worker зберігає ID маршруту та імена виконавця й QA. Після успішних тестів окремий QA-агент перевіряє патч за критеріями плану. Оператор може натиснути **«Завершити»** після схвалення QA.

## Локальна вправа без Slack і Jira

У каталозі `backend` виконай `.venv/bin/python -m app.workshop_exercise`. Потрібен доступ до моделі через Claude Code. Команда використовує тимчасову базу та відповіді з фікстури бронювання. Додай `--reply incomplete`, щоб дати неповну відповідь і перевірити додаткове уточнення.

1. Збережи перший результат у файл, наприклад через `| tee /tmp/workshop-before.txt`.
2. Зміни одне правило в `.claude/skills/workshop-tone-of-voice/SKILL.md` у корені репозиторію.
3. Повтори ту саму команду й порівняй формулювання уточнень та чернетки на тих самих вхідних даних.

## Підключення до спільного Slack-бота

Маршрутизатор запускається окремо від локального бекенду учасника. З каталогу `backend` запусти `uvicorn app.slack_router:app` з окремим `DATA_DIR`. Для живого підключення задай `WORKSHOP_SLACK_WORKSPACE_ID` і `WORKSHOP_SLACK_SIGNING_SECRET` у процесі маршрутизатора. У Slack-застосунку підпиши бота на `message.im` і вкажи HTTPS-адресу маршрутизатора з шляхом `/slack/events`. Маршрутизатор перевіряє підпис, час запиту й workspace. Поточний транспорт W09 — Slack Events API через підписаний HTTP. [Подія message.im](https://docs.slack.dev/reference/events/message.im/) · [Підписи Slack](https://docs.slack.dev/authentication/verifying-requests-from-slack/)

У локальному бекенді задай `WORKSHOP_SLACK_ROUTER_URL`. Доки немає екрана W12, підключення можна пройти через локальний API.

1. Виклич `POST /api/jira/workshop/pairing`. Отримаєш одноразовий код, дійсний п’ять хвилин. Новий запит до підтвердження замінює попередній код.
2. Надішли `pair <код>` у приватний діалог зі спільним ботом.
3. Перевір `GET /api/jira/workshop/pairing`. Статус `connected` містить підтверджені Slack ID, ID активованого профілю та тестовий `reporter_id`. Локальний бекенд зберігає їх, а scheduler підхоплює профіль у наступному циклі. Для створення навчальної задачі передай цей `reporter_id` у `POST /api/jira/training/issues`.

Повторний запит статусу або перезапуск із тими самими базами відновлює прив’язку. Живий тест потребує доступу до Slack-застосунку. Для перевірки без Slack запусти з каталогу `backend` `.venv/bin/python -m pytest -q tests/test_workshop_pairing.py`, щоб перевірити сценарій на підписаних тестових подіях.

## Відкриття Slack-треду

Для живого відкриття тредів у процесі маршрутизатора задай `WORKSHOP_SLACK_CHANNEL_ID` і `WORKSHOP_SLACK_BOT_TOKEN`. Боту потрібен доступ до спільного каналу та дозвіл `chat:write`. Репортер має бути учасником каналу, щоб Slack сповістив його про згадку. [Публікація повідомлень](https://docs.slack.dev/reference/methods/chat.postMessage/) · [Згадки користувачів](https://docs.slack.dev/messaging/formatting-message-text/#mentioning-users)

Worker передає операцію `<run_id>:thread` маршрутизатору. Бот публікує початкове повідомлення зі згадкою репортера, ключем задачі й джерелом Jira. Маршрутизатор зберігає Slack timestamp перед отриманням permalink, а локальний worker записує канал, timestamp і посилання в прогін. Повтор запиту повертає збережений результат. Якщо не вдалося отримати permalink, повторюється лише цей запит. [Посилання на повідомлення](https://docs.slack.dev/reference/methods/chat.getPermalink/)

Якщо Slack міг прийняти повідомлення, але підтвердження відсутнє, операція переходить у `unknown`, а прогін потребує ручної перевірки. Маршрутизатор не надсилає друге повідомлення.
